# Configure Remote Application Access

**Status:** Planned; not deployed for any HomeLab service. Related to [Publish Portfolio Website](publish-portfolio-website.md), [Onboard Home Assistant](onboard-home-assistant.md), [Deploy Nextcloud](deploy-nextcloud.md), and [Deploy Bitwarden](deploy-bitwarden.md).

The earlier target used the owner's future domain and separately reviewed Cloudflare Tunnel routes for the public portfolio site at the domain apex and for Home Assistant, Nextcloud, and production Bitwarden on distinct subdomains. The later dated access-path refinement below favors a public HTTPS reverse proxy for Jellyfin, Nextcloud, and Bitwarden so native apps and streaming traffic use one ordinary URL per service. These are planned names and routes only. A published application route exposes that application's login or content to the internet; a tunnel or reverse proxy does not itself authenticate users.

**2026-10-01 access requirements:** The intended Nextcloud, Bitwarden, and Jellyfin services should work in a browser and native apps away from home without Tailscale, with strong MFA. Do not mark this achieved from browser-only testing. Nextcloud and Bitwarden provide application-level MFA paths; the selected Jellyfin version and clients need a verified MFA-compatible design before public access. Cloudflare Access browser login redirects may block native clients, so require real extension, desktop, mobile, and media-client tests before adding Access in front of a service. [Cloudflare describes the default non-browser redirect limitation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/).

**2026-10-01 authentication clarification:** Strong MFA is required for Nextcloud and Bitwarden, not for Jellyfin. The Jellyfin public route may use its own account login and optional Roku Quick Connect after service isolation, HTTPS, restricted proxy-to-origin access, updates, account lockout, and external-client tests. Do not place a browser-only identity challenge in front of the Roku app. The earlier Jellyfin MFA gate above is superseded by this clarification; third-party Jellyfin MFA plugins are optional research rather than a publication dependency.

**2026-10-01 access-path refinement:** For Jellyfin, Nextcloud, and Bitwarden, the preferred design candidate is one small public VPS running an HTTPS reverse proxy, connected privately to the HomeLab by an outbound-established WireGuard/Tailscale link. Public `media`, `drive`, and `pass` DNS records would point to that VPS with Cloudflare **DNS-only**; client devices would open ordinary HTTPS URLs and need no VPN software. This bypasses Cloudflare's video proxy and request-size limitations while retaining Cloudflare Registrar/DNS if chosen. It also means Cloudflare WAF, Access, and other proxy features do not protect these records. [Cloudflare explains DNS-only behavior](https://developers.cloudflare.com/dns/proxy-status/); [Jellyfin documents VPS reverse proxy as a remote-access method](https://jellyfin.org/docs/general/post-install/networking/). The observed provider-side shared IPv4 and absent connected IPv6 from 2026-09-14 make direct home forwarding an unproven option; first recheck current WAN/public IPv4, IPv6, both router NAT layers, and ISP options. If a stable publicly reachable address is available, an isolated home reverse-proxy guest with one narrowly forwarded HTTPS port is a possible simpler variant. Do not publish the NAS UI, SSH, Docker API, SMB, NFS, or management tools.

The VPS would hold no primary application data; it would terminate public TLS, route only named application hosts to their origin ports, and restrict the private link and NAS/router firewall to those destinations. The private link may use Tailscale **between servers** without requiring it on Roku, phones, or other clients. Connector placement, whether the NAS can maintain this link independently of Proxmox, VPS/provider traffic allowance, DNS/certificates, external monitoring, and recovery remain `TODO`. For example, [DigitalOcean's current basic VPS pricing](https://www.digitalocean.com/pricing/droplets) starts at $6/month for 1 GiB RAM with 1,000 GiB included outbound transfer; [overage is billed separately](https://docs.digitalocean.com/platform/billing/bandwidth/). This is an example cost, not a provider selection. At 8 Mb/s, one hour of continuous streaming transfers about 3.6 GB; measure actual use and home upload before choosing a plan.

Without local DNS routing, even a Roku at home using the public name would stream through the VPS, consuming home upload and VPS outbound allowance. Test the public URL first, then evaluate split DNS or a local reverse proxy using the **same HTTPS hostname and trusted certificate** for LAN clients, only if the Archer/router-VM DNS path supports it. Avoid a different insecure local URL as the assumed everyday client configuration. A public VPS and private link add their own availability dependencies; monitor both from outside the HomeLab and keep local recovery access.

Use each application's native authentication rather than a browser-only proxy challenge on app routes. [Nextcloud documents TOTP/FIDO2 and per-device app passwords](https://docs.nextcloud.com/server/latest/user_manual/en/user_2fa.html); [Bitwarden documents FIDO2 WebAuthn and authenticator two-step login](https://bitwarden.com/help/setup-two-step-login/). Require MFA for their account enrollment and supported login flows, with revocable long-lived client sessions/tokens afterwards. Jellyfin's official [Roku Quick Connect](https://jellyfin.org/docs/general/server/quick-connect/) can approve a TV from an already signed-in device; it is an optional convenience alongside a strong unique Jellyfin account password and tested account lockout. Jellyfin MFA plugins are optional and must be reviewed separately if later desired.

[Nextcloud AIO documents Cloudflare Proxy/Tunnel limitations](https://github.com/nextcloud/all-in-one#notes-on-cloudflare-proxytunnel), including upload-size and timeout limits, domain validation, and local access behavior. Test representative large uploads and synchronization before accepting that route. [Cloudflare's Tunnel FAQ](https://developers.cloudflare.com/cloudflare-one/faq/cloudflare-tunnels-faq/#large-file-and-streaming-traffic-through-tunnel) says public hostname routes carrying video and other large files on Free, Pro, and Business plans require an applicable paid service. Do not assume an ordinary public Tunnel route can carry Jellyfin streaming; choose a permitted delivery path and verify Roku/client compatibility and Jellyfin account controls before publishing it.

The owner is open to a reasonably priced Cloudflare subscription and registering the future domain with [Cloudflare Registrar](https://developers.cloudflare.com/registrar/). Check the exact domain's registration and renewal prices before purchase. [Pro and Business pricing](https://www.cloudflare.com/plans/) does not itself permit local Jellyfin video over a public Tunnel; [Cloudflare's delivery guidance](https://developers.cloudflare.com/fundamentals/reference/policies-compliances/delivering-videos-with-cloudflare/) names Stream and Enterprise Stream Delivery as video options. Stream has [usage-based storage and delivery charges](https://developers.cloudflare.com/stream/pricing/) and is not a verified Jellyfin integration. Keep remote Jellyfin media routing unresolved; use paid Cloudflare features for other routes only when they solve a measured need.

Place connectors where they can reach only the intended origin service and port. Whether to use one connector per zone/service, where Home Assistant's Archer-side connector runs, Cloudflare Access policy, certificate/origin settings, native-client compatibility, and availability dependencies remain `TODO`. A Cloudflare Access login must be tested with Home Assistant, Nextcloud sync, and Bitwarden clients before adoption. Do not publish Proxmox, switch management, Homepage, Uptime Kuma administration, the Minecraft web panel, or the Acer host administration through this plan.
