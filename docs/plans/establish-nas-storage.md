### Initial pool and allocation design

Create an SSD Basic pool/volume for NAS-local Compose projects, databases, Jellyfin metadata/cache, and any tested light VM image. Create a separate 4 TB-class HDD Basic pool/volume for `media`, `nextcloud-data`, `proxmox-backups`, `minecraft-backups`, `ai-data`, and other service-specific backup shares. Names are illustrative, not configured paths. Keep headroom for Btrfs snapshots, Nextcloud file versions/trash, growing backups, RAID conversion, and normal write operation. A 4 TB advertised disk supplies less usable space after formatting; the eventual two-disk RAID 1 supplies approximately one disk's usable capacity, not 8 TB. The single initial SSD and HDD can each fail independently; the later HDD mirror does not protect the SSD. Consider a second M.2 SSD or independent SSD backup once application data becomes important.

Use one or a few Btrfs volumes and separate shared folders with per-folder quotas and permissions first; dedicated volumes are useful only where a hard capacity boundary or different volume policy is needed. Avoid preallocating rigid multi-terabyte volumes before actual usage is known. [UGOS Pro describes pools, volumes, Btrfs, quotas, and Basic-to-RAID-1 conversion](https://support.ugnas.com/detail/article/en-US/305), and [shared-folder permissions and NFS client rules](https://support.ugnas.com/detail/article/en-US/494). Create a nonadministrator identity or export rule per remote consumer, grant only its own share, and keep `media` read-only to Jellyfin. A Docker bind mount on the NAS uses host filesystem permissions and mount mode rather than an SMB login; test numeric UID/GID behavior for the selected images. UGOS administrators and the Docker daemon remain able to access underlying data, so this is operational separation, not a hard security boundary.

For cross-VLAN storage, route only the actual consuming host to the NAS storage address and required protocol/port through the router-VM firewall. Proxmox can mount a restricted NFS or SMB backup share; the Pi and Acer can use separate NFS/SMB or a controlled backup-push method. Require per-client NFS rules or per-service SMB identities as applicable, plus NAS firewall rules; avoid wildcard exports or one all-purpose credential. A service hosted directly on the NAS should read its local bind mount or a tested VM-to-host share, without an unnecessary trip through the router. Do not present the NAS's entire volume to a remote guest merely to reach one folder. The switch access VLAN separates the NAS from other VLANs, but cannot separate its own containers from one another. [UGOS Pro documents SMB, NFS, and rsync services](https://support.ugnas.com/detail/article/en-US/77); [Proxmox supports NFS/SMB backup storage](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf). Keep active Proxmox VM disks local initially: network-backed VM disks would add a dependency on NAS, switch, and router availability and are unnecessary for backup use.

### UGOS Pro management, recovery, and OS choice

UGOS Pro is sufficient for this **small NAS and secondary-host design** if its firmware passes on-device tests. Its documented tools include separate pools and volumes, Btrfs shared-folder snapshots and quotas, user/group and share permissions, capacity/drive alerts, Basic-to-RAID-1 conversion, Docker Compose projects, light VMs with snapshot/OVA export, SMB/NFS/rsync, and scheduled Sync & Backup tasks including remote and external targets. [Storage](https://support.ugnas.com/detail/article/en-US/313), [snapshots](https://support.ugnas.com/detail/article/en-US/654), [backup/restore](https://support.ugnas.com/detail/article/en-US/401), [Docker projects](https://support.ugnas.com/detail/article/en-US/411), and [VM management](https://support.ugnas.com/detail/article/en-US/229) are vendor-documented features; firmware/model-specific behavior and application restore still need tests. UGOS Pro also offers administrator SSH/root access, but direct system edits are not a documented durable configuration interface for VLANs or storage policy.

For this two-bay Basic/RAID-1 design, do not count on the vendor's pool `Data Organizing`/scrub feature: [UGREEN documents it only for RAID 5/6](https://support.ugnas.com/detail/article/en-US/638). Btrfs snapshots help reverse deletion or unwanted changes but stay on the same storage system; they are not an independent backup, and a live database snapshot may not be application-consistent. Schedule application-aware exports or database dumps together with data/configuration, copy selected backups off the NAS to an external disk or another location, and prove a full restore. [UGOS Pro supports external-drive backup](https://support.ugnas.com/detail/article/en-US/679). A factory reset retains disk files according to UGREEN but clears NAS settings and installed apps; preserve Compose definitions, share/permission configuration, backup jobs, and recovery instructions outside the NAS. [Factory-reset scope](https://support.ugnas.com/detail/article/en-US/465).

UGREEN states that [third-party systems such as Unraid or TrueNAS can be installed but are not officially supported and may cause problems](https://ai-eu.ugreen.com/pages/service). Thus the hardware is replaceable-OS-capable in principle, but alternate-OS boot, drivers, fan control, recovery of UGOS, and the L1 refurbished warranty impact are `UNKNOWN` for this exact unit. A different OS would replace the UGOS management and app features above and may require changing the disk layout. Plan on supported UGOS Pro settings and Compose/VM interfaces first; keep data and application backups portable so an OS migration remains possible later. Do not overwrite or repartition the factory boot device merely to experiment after receiving the NAS.

[UGOS Pro added Amazon S3 Cloud Drives support in 2026](https://support.ugnas.com/detail/article/en-US/919). Its [S3 connection guide](https://support.ugnas.com/detail/article/en-US/861) documents manual upload/download and a scheduled sync workflow on supported firmware. A separate general [Cloud Drives guide](https://support.ugnas.com/detail/article/en-US/376) lists S3 as connectable but omits it from its enumerated sync-capable services, so confirm the exact installed app/firmware behavior. Even when available, file sync may propagate deletions or corrupt files; do not treat a one-way mirror as the only disaster backup. [UGOS Pro's own backup guide](https://support.ugnas.com/detail/article/en-US/401) distinguishes backup from sync. A candidate alternative is a maintained backup tool such as [Kopia](https://kopia.io/docs/) or [restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) running with read-only access to staged, application-consistent backup inputs and writing encrypted, versioned snapshots to S3. Validate restore on a different machine before selecting the implementation.

Use client-side encryption for private content before upload; AWS's default server-side encryption alone does not keep plaintext from a party with authorized S3 read access. Keep encryption recovery keys outside the NAS and outside this repository. Use a dedicated least-privilege AWS identity, private bucket with [Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html), and a separate retention/deletion control. [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html) can preserve versions against deletion for a defined period, but requires versioning and increases retained capacity; test the selected backup tool's pruning behavior before enabling it. Restore needs both surviving cloud access and the independent encryption key. Do not upload live, inconsistent databases or unprotected vault exports.
