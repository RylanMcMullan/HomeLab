## 2026-10-06 — Reported management reachability interruption

The operator reported that the Proxmox web UI on the HP EliteDesk was unreachable over local Wi-Fi and Tailscale, then powered the node off and back on. The cause, duration, guest impact, and post-restart reachability are `UNKNOWN`; no logs or host-health evidence were collected for this report. Diagnose management reachability and host health before depending on the HP for a public portfolio origin. This report does not establish that Tailscale, Proxmox, or the physical host was the failing component.

**2026-10-06 follow-up, verified through the Proxmox host shell after the restart:** The web UI and shell were reachable. The prior boot's kernel journal contained 216,745 `e1000e ... Detected Hardware Unit Hang` messages, first observed in that journal on 2026-10-01 at 16:31 and still repeating at 16:56 on 2026-10-06. The NIC negotiated 100 Mb/s full duplex in the prior boot and again after restart; its link partner advertised only 10/100 Mb/s modes at the time checked. The current boot had no matching hang message in the inspected log, and `systemctl --failed` listed no failed units. The host's NVMe SMART overall-health check passed, with approximately 139 million KiB available in `local-lvm` and 61 million KiB in `local` at the check. These observations identify a persistent network fault and sufficient storage for a small guest, but do not prove sustained stability or identify whether cable, switch port, NIC hardware, or driver is responsible. No website VM was created during this check.

**2026-10-06 NIC mitigation and follow-up:** The NIC was identified as an Intel Ethernet Connection (7) I219-LM using the `e1000e` driver on kernel `7.0.2-6-pve`. The operator reported that the HP's switch port showed 100 Mb/s after reseating the same cable in the same port; other devices on that switch showed 1 Gb/s. A known-good cable and port substitution has not yet been performed, so the cause remains `UNKNOWN`. Energy Efficient Ethernet was enabled but inactive when checked. Segmentation and receive offloads were initially enabled. As a reversible software mitigation, `ethtool -K nic0 tso off gso off gro off` disabled those three offloads. A systemd oneshot service at `/etc/systemd/system/nic0-offloads.service` now runs that exact command at boot. `systemctl enable --now nic0-offloads.service` succeeded, the service was active (exited), and `ethtool -k nic0` showed all three offloads off. At the follow-up check, the current boot had zero hardware-hang messages, zero selected NIC error/timeout counters, and a three-packet external ping had no loss. The link still negotiated 100 Mb/s. Boot persistence and long-term stability remain unverified; this mitigation is not a confirmed root-cause repair. If needed, revert with `systemctl disable --now nic0-offloads.service`, remove the service file, run `systemctl daemon-reload`, and restore the three offloads with `ethtool -K nic0 tso on gso on gro on`.

**2026-10-06 cable substitution, verified:** The operator moved the HP to a new cable and a switch port that had previously served another gigabit device. The switch showed its gigabit indicator, and `ethtool nic0` then reported 1,000 Mb/s full duplex with autonegotiation enabled. Selected NIC error, CRC, and transmit-timeout counters remained zero; no hardware-hang message was present in the current boot's inspected kernel log. This isolates the 100 Mb/s symptom to the former cable/port path, but does not distinguish the old cable from the old port or prove that path caused the earlier hangs. The offload mitigation remained active. The displaced device's new connection state was not checked.

**2026-10-06 portfolio VM preparation, verified:** The official Debian 13.7.0 AMD64 netinst ISO downloaded successfully to Proxmox `local` storage and passed `sha512sum -c` against the official Debian `SHA512SUMS`. A dedicated `portfolio-web` VM was created with one vCPU, 2 GiB RAM, a 16 GiB disk on `local-lvm`, the installer ISO attached, guest-agent support configured, and automatic start disabled. `qm status` showed it stopped; its configuration had no virtual NIC. Debian has not been installed and the guest has no network access or public route. Private guest and storage identifiers are omitted from this repository.

**2026-10-06 final link follow-up:** After the operator reseated the black cable at the patch-panel coupler and returned the HP to switch port 2, the Proxmox host again verified 1,000 Mb/s full duplex. Selected NIC error and timeout counters and the current boot's matching hardware-hang count remained zero; five external ICMP probes had no loss. The offload mitigation service was active, and the portfolio VM was still stopped with no virtual NIC. See the [network diagnosis](network-discovery.md#2026-10-06--patch-coupler-seating-diagnosis). The physical 100 Mb/s negotiation symptom appears resolved; the older NIC hangs and mitigation's effect over a future reboot remain unproven.

The [individual Ethernet incident record](incidents/2026-10-06-hp-ethernet-link.md) links the host and network evidence and tracks the remaining checks.

## 2026-10-06 — Guest Startup, Resource Baseline, and Controlled Reboot

After the earlier manual restart, a fresh host check found the Tailscale LXC **stopped**. Its Proxmox configuration had `onboot: 0`, while the Home Assistant VM had `onboot: 1`; the uninstalled portfolio VM also had `onboot: 0`. This explains why the Tailscale service did not return automatically after that restart, but it does not establish why Proxmox was unreachable before the restart. The previous boot had repeated `e1000e` hardware-hang messages, including shortly before the manual reboot; the exact causal relationship to the reported management outage remains unproved.

The Tailscale LXC was started, its `onboot` setting was changed to `1`, and its startup order was set to `1`. The Home Assistant VM retained `onboot: 1` and was assigned startup order `2`. The portfolio VM remained stopped with automatic start disabled because its operating system and network are not configured. Inside the LXC, `tailscaled` was active and enabled. A parsed local `tailscale status --json` check showed backend `Running`, the local node online, and zero health messages; advertised routes and external client reachability were not inspected.

At the low-load pre-reboot check with Home Assistant and Tailscale running, the six-thread host used about 3.3 GiB of 15 GiB memory with about 12 GiB available, no swap in use, and a load average around 0.1. The root filesystem was about 10% used, and the 140.9 GiB LVM-thin pool about 5.7% physically allocated. The link was 1,000 Mb/s full duplex; selected RX/TX errors and transmit timeouts were zero, and the current boot showed zero matching hardware-hang messages. This is a single low-load sizing snapshot, not a peak or five-service stress test. The VM disks are thin-provisioned, so low physical allocation is not the same as unlimited safe future capacity.

A controlled Proxmox reboot was then requested through the web UI. The host returned, and the boot log showed the Tailscale LXC start task before the Home Assistant VM start task. Both guests were running; the portfolio VM remained stopped. Tailscale again reported backend `Running`, local node online, and zero health messages. The HP link negotiated 1,000 Mb/s full duplex, TSO/GSO/GRO were all off, `nic0-offloads.service` was active, selected NIC error/timeout counters were zero, and the new boot showed no `Detected Hardware Unit Hang` message at the check. This verifies the configured boot behavior and offload persistence once; sustained stability and the separate contributions of cabling and offload mitigation remain `UNKNOWN`.
